# Architecture

## Active system

The active codebase is a collection of versioned empirical studies rather than
a single strategy service. `evaluate/` contains loaders, indicator calculations,
state machines, M1 replay loops, statistical tests and MT5 reconciliation tools.
Some studies share helper modules; others deliberately freeze their own logic.
Preserving those implementations avoids silently changing earlier measurements.

| Layer | Main location | Responsibility |
| --- | --- | --- |
| Data qualification | `evaluate/*onboarding*`, `*source*`, `*qualification*` | Coverage, symbol semantics, price units and provenance |
| Hypothesis evaluation | `evaluate/` | Causal signals and execution under a frozen study specification |
| Native execution | `ea/`, `Include/` | MQL5 indicators, order management and guard experiments |
| Reconciliation | `evaluate/*parity*`, `*reconcile*`, `execution_safe_model4_v1.py` | Align Python/reference output with tester artifacts |
| Account/risk replay | `evaluate/ftmo_account_replay_v1.py`, portfolio/Monte Carlo studies | Account constraints and explicitly scoped simulations |
| Observation tools | `scripts/` | Quote/source capture and diagnostic helpers |
| Evidence | `data/results/<study>/` | Frozen declarations and reports; full runtime artifacts remain local |

Running a Python evaluation is not permission to run a live EA. The research
layers and terminal operations are separate steps with different dependencies.

## Native experts

`ORB_Strategy.mq5` and `SP2L_SpikeGap.mq5` are frozen reference EAs. Execution-safe
variants and later experimental EAs retain their own names. Regime controller
sources are generated by `evaluate/regime_rotation_build_ea.py`; changing an
embedded generated copy directly would break provenance.

The macro ensemble exposes two internal engines:

- Engine A: H4 EMA29/ATR29 Keltner breakout with a daily EMA50 filter and EMA ratchet.
- Engine B: H1 Donchian breakout, ADX filter and H4 Supertrend anchor with an ATR ratchet.

Exact bucket definitions, stop coordinates and financing vary between frozen
experiments. The presence of the same engine name does not prove implementation
parity across every study or with a broker's native candles.

## CAIRO archive

The historical CAIRO pipeline loaded externally trained models, calculated live
features, aggregated votes and served signals through HTTP/socket transports.
A C bridge and MQL5 EA connected that service to MT5. Queue and terminal helpers
orchestrated fold evaluations.

Those modules are preserved together under `archive/legacy/` so their original
imports have a coherent root. Their integration tests, historical guide and
configuration are not mixed with the active offline suite. External model
implementations, trained weights and database contents remain unavailable in
the public source release.

## Portability boundary

The synthetic example and default offline tests are intended to run without
market data. Full historical studies can require original data revisions,
local Windows paths, a specific MT5 symbol store, Node-based download tools or
additional research packages. Public source is not a containerized reproduction
of every historical machine state.
